# Chapter 4 (DS): Evaluation done right

A model that scores 99% is not good news. It is a question: *what did I do wrong?* In real projects a number that looks too good is far more often a **mistake in the evaluation** than a miracle in the model. The mistake is quiet. No error message appears, no test fails, the code runs and prints a beautiful score. Months later the model goes into production, meets real data, and falls apart.

ds.03 taught you the honest basics: baselines, train/validation/test splits, cross-validation, metrics. This chapter is about everything that can go wrong *around* those basics, and how to build evaluation that survives contact with the real world. You will learn to find **data leakage** (information from outside the training world sneaking into the model), to split data the way the model will actually be used (**by group** and **by time**), to **beat a baseline and prove it**, to handle **rare classes** and pick a **threshold from a business cost**, to check whether predicted probabilities can be **trusted** (calibration), to look for **where the model fails** (error analysis), and to make every result **reproducible** and **identical in training and serving**.

By the end you reach the three outcomes of the syllabus: **find the leak in a model that looks too good**, **beat a simple baseline and prove it with the right split**, and **choose a threshold from a business cost**. The project hands you a deliberately leaky machine-learning project; you audit it, fix it, and write down the true score.

Prerequisites: ds.03 (splits, cross-validation, metrics, baselines) and ds.02 (logistic regression). Pipelines appear here because they are the cure for the most common leak; ds.05 teaches them in depth.

> **Offline rule for this chapter.** Everything runs with no internet, using NumPy, pandas and scikit-learn. All data are **synthetic and seeded**, generated by a known rule, so we always know the truth the model should find. That is on purpose: with real data you never know whether a score is too good; with a data generator you do. ## 1. The model that looked too good

### 1.1 A story you will meet in real life

A telecom company wants to predict which customers will **cancel next month** (*churn*), so the retention team can call them first. An analyst builds a model on last year's customers and reports:

> "Cross-validated AUC is 0.97. The model is almost perfect."

The team celebrates. The model is deployed. A month later the retention team says the calls are not reaching the right people, and the real-world AUC measured on new customers is about 0.75. Nothing in the code was "broken". The model did exactly what it was asked. The *evaluation* was wrong.

We will recreate this story with data we control. The generator below builds customers with a known rule: customers on **month-to-month contracts**, with **short tenure**, many **support calls**, a **high monthly charge** and **no autopay** are more likely to churn. The `leaks=True` option adds one extra column, `retention_offer_sent`, that we will come to understand.

```python run
def make_churn(n=4000, seed=0, leaks=False):
    """Synthetic telecom customers. The true churn rule is known and noisy."""
    r = np.random.default_rng(seed)
    contract = r.choice(["month", "year", "two_year"], n, p=[.55, .25, .20])
    tenure = np.clip(r.gamma(2.2, 12, n), 1, 72).round()
    charge = np.clip(r.normal(65, 22, n), 20, 120).round(2)
    calls = r.poisson(1.2 + 0.03 * (charge - 65) / 10 + 0.6 * (contract == "month"), n)
    autopay = r.random(n) < 0.5
    region = r.choice(["north", "south", "east", "west"], n)
    logit = (-1.6 + 1.1 * (contract == "month") - 0.9 * (contract == "two_year")
             - 0.025 * tenure + 0.018 * (charge - 65) + 0.38 * calls - 0.5 * autopay)
    churn = (r.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    df = pd.DataFrame(dict(tenure_months=tenure, monthly_charge=charge, support_calls=calls,
                           contract=contract, autopay=autopay.astype(int), region=region,
                           churned=churn))
    if leaks:
        # Written AFTER the customer decided: 92% of churners got an offer, only 4% of stayers.
        df["retention_offer_sent"] = np.where(churn == 1, r.random(n) < 0.92,
                                              r.random(n) < 0.04).astype(int)
    return df

churn = make_churn(leaks=True)
print(churn.shape, "| churn rate:", round(churn["churned"].mean(), 3))
print(churn.head(6).to_string())
```

### 1.2 Two evaluations of the same model

Below we score the **same algorithm** twice, once without and once with the suspicious column. The only difference is one column.

```python run
Xall = pd.get_dummies(churn.drop(columns="churned"), dtype=float)
yall = churn["churned"]
honest_cols = [c for c in Xall.columns if c != "retention_offer_sent"]

def cv_auc(model, X, y, cv=5):
    scores = model_selection.cross_val_score(model, X, y, cv=model_selection.StratifiedKFold(cv, shuffle=True, random_state=0), scoring="roc_auc")
    return scores.mean(), scores.std()

lr = pipeline.make_pipeline(preprocessing.StandardScaler(), linear_model.LogisticRegression(max_iter=2000))
for name, cols in [("without retention_offer_sent", honest_cols), ("with    retention_offer_sent", list(Xall.columns))]:
    m, s = cv_auc(lr, Xall[cols], yall)
    print(f"{name}: AUC {m:.3f} +- {s:.3f}")
```
```text
without retention_offer_sent: AUC 0.759 +- 0.032
with    retention_offer_sent: AUC 0.968 +- 0.006
```

The column `retention_offer_sent` lifts AUC from "decent" to "almost perfect". Why would an offer column be so informative? Because in this company the offer is sent **when a customer calls to cancel**. The column is *recorded after the outcome*. At the moment we must predict (before the customer decides) the column does not exist yet, so on the day of deployment it will be empty or zero for everyone. The model learned "customers who got an offer churned", which is true in the history and useless in the future.

> **Predict the output.** We train on the leaky column, then test on *future* customers for whom the offer has not been sent yet (the column is all zeros). Will the AUC stay near 0.97, or fall? And what will happen to the predicted probabilities?

<details><summary>Answer</summary>

The AUC falls to the honest level (about 0.77): the 0.97 was never real. AUC only looks at the *ordering* of customers, and a column that is constant for everybody cannot change an ordering. The damage is worse in another place: the model believes "no offer sent means safe", so every probability it prints is far too low. A team that acts on "probability above 0.5" would find almost nobody, even though a quarter of the customers leave.

```python run
trainset = churn.sample(frac=0.7, random_state=1)
future = churn.drop(trainset.index).copy()
future["retention_offer_sent"] = 0          # not yet known at prediction time
def fit_eval(cols):
    Xtr = pd.get_dummies(trainset.drop(columns="churned"), dtype=float)[cols]
    Xte = pd.get_dummies(future.drop(columns="churned"), dtype=float)[cols]
    mdl = pipeline.make_pipeline(preprocessing.StandardScaler(), linear_model.LogisticRegression(max_iter=2000)).fit(Xtr, trainset["churned"])
    p = mdl.predict_proba(Xte)[:, 1]
    return metrics.roc_auc_score(future["churned"], p), p.mean(), metrics.recall_score(future["churned"], p > 0.5)
for name, cols in [("honest model", honest_cols), ("leaky  model", list(Xall.columns))]:
```

### 1.3 The lesson, in one sentence

> **A score is only as honest as the question the evaluation asks.** The honest question is: *if I train on what I knew then, how well do I predict what happened next, on data I have never touched?* Every section of this chapter is a different way that question gets quietly replaced by an easier one.

### 1.4 A cheap alarm: "too good" is a signal

Rules of thumb for the first five minutes of any project:

| You see | Suspect |
|---|---|
| A score much better than a published or domain-expert ceiling | leakage, duplicates |
| One feature that alone gives near-perfect prediction | target leakage |
| Training score and validation score both ~100% | the target (or a copy of it) is in the features |
| A big drop from validation to production | split does not match deployment (time, group) |
| Test score is *higher* than validation score, repeatedly | the test set has been used for tuning |
| Random-label test (shuffle `y`) still scores above chance | pipeline leaks |

The last row is a powerful tool: the **permutation sanity check**. If you shuffle the labels, no honest pipeline can score better than chance. We use it in section 4.

## 2. Data leakage: what it is and the four families

### 2.1 Definition

**Data leakage** means the model, during training or model selection, had access to information that will not be available when it is used for real predictions (or that it should not have been allowed to see while being evaluated). Leakage makes estimates optimistic. It does not make models crash; it makes them *lie*.

Think of an exam. Leakage is when the student saw the exam questions the night before. The mark is real, but it no longer measures what you wanted to measure.

### 2.2 Four families

| Family | In words | Example | Cure |
|---|---|---|---|
| **1. Target leakage** | a feature is made after, or from, the outcome | `retention_offer_sent`; "discharge diagnosis" used to predict admission | ask when each column is created; drop it (section 4) |
| **2. Preprocessing leakage** | statistics (mean, scaler, feature choice, imputation) are learned from rows that later become test rows | scaling the whole dataset, then splitting | fit every learned step inside the training fold (section 3) |
| **3. Split leakage** | rows in the test set are copies or close relatives of training rows | the same patient in train and test; duplicate rows; same customer different month | split by group (section 6), deduplicate (section 5) |
| **4. Time leakage** | the model sees the future | random split of a time series; a feature that uses data after the prediction date | split by time (section 7), build features from the past only |

A fifth source is not about data but about *you*: **evaluation leakage by selection**. If you try 50 models and report the best test score, the test set has become part of training (ds.03 section 10). Keep that in mind throughout.

### 2.3 The golden rule

> **Anything that learns something from data must be fitted using the training rows only, and the thing it learns must be applied (not re-learned) to validation and test rows.**

"Learns something" is broader than "a model". A mean is learned. A standard deviation is learned. A vocabulary, a list of categories, a set of selected columns, a PCA basis, a median used to fill gaps, an outlier cut-off: all of these are *fitted*. In scikit-learn terms, everything with a `fit` method.

The corollary for splits: **the split must copy how the model will be used**. If the model will predict next month's customers, the test set must be next month's customers. If it will predict for patients it has never seen, the test set must be patients it has never seen.

## 3. Preprocessing before splitting

### 3.1 The most famous leak: choosing features on all the data

Here is a startling experiment. We create a dataset of **100 rows and 2,000 columns of pure random noise**, and labels chosen by a coin flip. There is nothing to learn. Any honest model must score about 50%.

The leaky recipe: (1) pick the 20 columns most correlated with the label, using *all* 100 rows; (2) cross-validate a classifier on those 20 columns.

```python run
rng = np.random.default_rng(1)
Xnoise = rng.normal(size=(100, 2000))
ynoise = rng.integers(0, 2, 100)
cv5 = model_selection.StratifiedKFold(5, shuffle=True, random_state=0)
clf = linear_model.LogisticRegression(max_iter=2000)

# LEAKY: select first (looks at every label), then cross-validate
Xsel = feature_selection.SelectKBest(feature_selection.f_classif, k=20).fit_transform(Xnoise, ynoise)
leaky = model_selection.cross_val_score(clf, Xsel, ynoise, cv=cv5).mean()

# HONEST: selection is part of the model, so each fold selects using its own training rows
honest_model = pipeline.make_pipeline(feature_selection.SelectKBest(feature_selection.f_classif, k=20), clf)
honest = model_selection.cross_val_score(honest_model, Xnoise, ynoise, cv=cv5).mean()
print(f"leaky  accuracy on pure noise: {leaky:.3f}")
print(f"honest accuracy on pure noise: {honest:.3f}   (chance is 0.5)")
```
```text
leaky  accuracy on pure noise: 0.860
honest accuracy on pure noise: 0.470   (chance is 0.5)
```

The leaky number looks like a real result. It is entirely fake. Among 2,000 random columns, some are correlated with *any* given labelling purely by luck. Selecting them using all rows means the test rows helped pick the lucky columns, so of course those columns "predict" the test rows.

### 3.2 Why a pipeline cures it

A scikit-learn **Pipeline** is a chain of steps that behaves like one model: `fit` fits every step in order on the training data, and `predict` only *applies* them. When you hand a pipeline to `cross_val_score`, each fold calls `fit` on that fold's training rows only. The selection step therefore never sees the held-out rows.

```python run
steps = pipeline.Pipeline([("select", feature_selection.SelectKBest(feature_selection.f_classif, k=20)),
                           ("clf", linear_model.LogisticRegression(max_iter=2000))])
print(steps)
# Inside one fold, by hand: this is exactly what cross_val_score does for you
tr, te = next(cv5.split(Xnoise, ynoise))
steps.fit(Xnoise[tr], ynoise[tr])                  # fit: selection learns from train rows only
chosen = steps.named_steps["select"].get_support(indices=True)
print("columns chosen from the 80 training rows:", chosen[:8], "...")
print("fold accuracy on 20 held-out rows       :", steps.score(Xnoise[te], ynoise[te]))
```
```text
Pipeline(steps=[('select', SelectKBest(k=20)),
                ('clf', LogisticRegression(max_iter=2000))])
columns chosen from the 80 training rows: [ 23  45  98 250 261 298 325 589] ...
fold accuracy on 20 held-out rows       : 0.5
```

### 3.3 The scaler leak (small, but common)

Standardising uses a mean and a standard deviation. If you compute them on all rows and then split, the test rows have contributed to those numbers. The effect is usually small for a plain scaler, but it is a leak, and the habit that allows it allows the big ones.

```python run
Xc = Xall[honest_cols].to_numpy()
yc = yall.to_numpy()
Xtr, Xte, ytr, yte = model_selection.train_test_split(Xc, yc, test_size=0.25, random_state=0, stratify=yc)

# WRONG: statistics from all rows
sc_all = preprocessing.StandardScaler().fit(Xc)
# RIGHT: statistics from training rows only
sc_tr = preprocessing.StandardScaler().fit(Xtr)
print("column 0 (tenure) mean used  | all rows:", round(sc_all.mean_[0], 3), "| train rows only:", round(sc_tr.mean_[0], 3))
print("test-set mean of tenure after RIGHT scaling:", round(float(sc_tr.transform(Xte)[:, 0].mean()), 3), "(not exactly 0: that is honest)")
print("test-set mean of tenure after WRONG scaling:", round(float(sc_all.transform(Xte)[:, 0].mean()), 3))
```
```text
column 0 (tenure) mean used  | all rows: 26.442 | train rows only: 26.604
test-set mean of tenure after RIGHT scaling: -0.039 (not exactly 0: that is honest)
test-set mean of tenure after WRONG scaling: -0.029
```

Note the honest test mean is not exactly zero. That is the point: the test rows are a *different sample*, and the model has to cope with data that does not look perfectly centred. Wrong scaling hides that.

### 3.4 Other learned preprocessing that leaks

Anything that learns from rows must go inside the training fold:

| Step | What it learns | Leaks if fitted on all rows |
|---|---|---|
| `StandardScaler`, `MinMaxScaler` | mean, std, min, max | yes (mild) |
| `SimpleImputer` | mean/median/mode to fill gaps | yes |
| `OneHotEncoder` | the list of categories | yes (a test-only category should be "unknown", not known) |
| Target/mean encoding | the average target per category | **severe** (the target itself leaks) |
| `SelectKBest`, `VarianceThreshold` | which columns to keep | **severe** when there are many columns |
| `PCA` | directions of variance | mild to moderate |
| Outlier clipping at the 99th percentile | the percentile | mild |
| SMOTE or any resampling | synthetic rows made from neighbours | **severe** if done before splitting |

### 3.5 Target encoding: the severe case

Target (mean) encoding replaces a category by the average of the target in that category. It is powerful, and a perfect trap. Consider a column with *many* categories, like `postcode`, where most postcodes have two or three customers. Replacing the postcode by "average churn in that postcode" computed on **all** rows gives every row a feature that *contains its own label*.

```python run
rng = np.random.default_rng(5)
n = 600
zip_code = rng.integers(0, 300, n)                  # 300 postcodes, about 2 customers each
y_zip = rng.integers(0, 2, n)                       # labels are pure coin flips: no real signal
frame = pd.DataFrame({"zip": zip_code, "y": y_zip})

# LEAKY: mean target per postcode over ALL rows, then split
frame["zip_enc_leaky"] = frame.groupby("zip")["y"].transform("mean")
tr_idx, te_idx = model_selection.train_test_split(frame.index, test_size=0.3, random_state=0)
m = linear_model.LogisticRegression().fit(frame.loc[tr_idx, ["zip_enc_leaky"]], frame.loc[tr_idx, "y"])
print("LEAKY  test accuracy:", round(m.score(frame.loc[te_idx, ["zip_enc_leaky"]], frame.loc[te_idx, "y"]), 3))

# HONEST: learn the postcode averages on the training rows only; unseen postcodes get the global mean
train_means = frame.loc[tr_idx].groupby("zip")["y"].mean()
global_mean = frame.loc[tr_idx, "y"].mean()
enc_tr = frame.loc[tr_idx, "zip"].map(train_means)
# Even the training rows must not see their own label: use leave-one-out for the training encoding
sums = frame.loc[tr_idx].groupby("zip")["y"].transform("sum")
cnts = frame.loc[tr_idx].groupby("zip")["y"].transform("count")
loo = ((sums - frame.loc[tr_idx, "y"]) / (cnts - 1)).fillna(global_mean)
enc_te = frame.loc[te_idx, "zip"].map(train_means).fillna(global_mean)
m2 = linear_model.LogisticRegression().fit(loo.to_frame("e"), frame.loc[tr_idx, "y"])
print("HONEST test accuracy:", round(m2.score(enc_te.to_frame("e"), frame.loc[te_idx, "y"]), 3), "  (labels are coin flips: expect about 0.5)")
```
```text
LEAKY  test accuracy: 0.783
HONEST test accuracy: 0.489   (labels are coin flips: expect about 0.5)
```

The leaky version is far above chance on labels that are pure luck, because each row's own label sits inside its encoded value. The honest version needs two protections: **fit on training rows only**, and for the training rows themselves use an **out-of-fold or leave-one-out** encoding so a row does not see its own answer. (scikit-learn has `TargetEncoder` which does the out-of-fold part for you; ds.05 uses it inside a pipeline.)

## 4. Target leakage and how to hunt it

### 4.1 The timeline question

For every column ask one question: **at the moment the prediction is made, is this value already known?** Draw a timeline. The prediction moment is a vertical line; every feature must come from the left of it, the target from the right.

```text
           past                  PREDICTION DAY                 future
  |---- signup ---- bills ---- support calls ----|---- cancel? ---- offer sent ---- refund ----|
  |<------------ usable features ---------------->|<----------- target and its consequences -->|
```

Columns on the right are **consequences of the target**: an offer made to those who threatened to leave, a refund issued after closure, "days since last login" measured at the data-export date for customers who have already gone. They are usually the strongest features, which is exactly why they are tempting.

> **Rule of thumb.** If a column is "too useful", ask *how was it created and by whom?* A column filled in by a person or a process that reacts to the outcome is a consequence, not a cause.

### 4.2 Detective tool 1: single-feature scores

A feature that alone predicts the target almost perfectly deserves suspicion. Score each feature on its own.

```python run
def single_feature_auc(X, y, cv=5):
    """Cross-validated AUC of a tiny model on one column at a time."""
    rows = []
    for col in X.columns:
        m = tree.DecisionTreeClassifier(max_depth=3, random_state=0)
        auc = model_selection.cross_val_score(m, X[[col]], y, cv=cv, scoring="roc_auc").mean()
        rows.append((col, auc))
    return pd.DataFrame(rows, columns=["feature", "single_feature_auc"]).sort_values("single_feature_auc", ascending=False)

print(single_feature_auc(Xall, yall).to_string(index=False))
```

### 4.4 Detective tool 3: the shuffled-label sanity check

Shuffle the target and run the *whole* pipeline again. If the score stays above chance, the pipeline leaks. If it falls to chance, the pipeline is at least not creating signal from nothing. Combine it with the earlier noise experiment and you have a regression test for evaluation code.

```python run
def shuffled_label_check(model, X, y, repeats=5, seed=0):
    r = np.random.default_rng(seed)
    scores = []
    for _ in range(repeats):
        ys = r.permutation(np.asarray(y))
        scores.append(model_selection.cross_val_score(model, X, ys, cv=5, scoring="roc_auc").mean())
    return float(np.mean(scores)), float(np.std(scores))

# 1. a sound pipeline on shuffled labels should sit at 0.5
print("sound pipeline, shuffled labels : AUC %.3f +- %.3f" % shuffled_label_check(lr, Xall[honest_cols], yall))
# 2. the leaky selection recipe from 3.1, on shuffled labels. Selection happens OUTSIDE cross-validation.
def leaky_selection_score(X, y, k=20):
    Xs = feature_selection.SelectKBest(feature_selection.f_classif, k=k).fit_transform(X, y)
    return model_selection.cross_val_score(linear_model.LogisticRegression(max_iter=2000), Xs, y, cv=5, scoring="roc_auc").mean()
print("leaky recipe, random labels     : AUC %.3f" % leaky_selection_score(Xnoise, ynoise))
```
```text
sound pipeline, shuffled labels : AUC 0.505 +- 0.010
leaky recipe, random labels     : AUC 0.968
```

### 4.5 Detective tool 4: ask the owner

No code replaces a conversation. For each suspicious column ask the data owner: *Who writes this? When? Can it change after the customer leaves? Does the system overwrite it?* Many leaks hide in fields that are **overwritten in place** ("current status", "last updated", "total spend to date"): the snapshot you downloaded contains the *final* value, not the value on prediction day.

### 4.6 Fixing it: rebuild the feature as of the prediction date

Dropping the column is the simple fix. A better fix, when the information is valuable, is to rebuild the feature **as of the prediction date**: not "total support calls ever" but "support calls in the 90 days before the cut-off date". That is a data-engineering task, and it is why good evaluation starts with a **cut-off date** written down for every dataset.

## 5. Duplicates and near-duplicates across the split

### 5.1 Why duplicates are leaks

If a row (or a near copy) lands in both training and test sets, the model is graded on something it memorised. Duplicates come from joins that multiply rows, data collected twice, web scraping that repeats pages, images that are crops of one another, and users with two accounts.

### 5.2 Measuring the damage

A flexible model such as a k-nearest-neighbours classifier with `k=1` memorises training rows. If the data hold copies, a random split lets it "recognise" test rows.

```python run
base = make_churn(n=1500, seed=11)

group_of_row = np.tile(np.arange(len(Xb)), 3)       # which original customer each row came from
```

## 6. Group-based splits

### 6.1 Rows are not independent

A random split assumes every row is an independent draw from the world. That is false whenever rows come in **families**: several visits by one patient, several photos of one object, several transactions by one card, several months of one customer. Rows in the same family share hidden traits. A model can learn "this is patient 17" from those traits and recall what happened to patient 17, which is useless for a new patient.

The question to ask: **at deployment, will the model see people (devices, stores, documents) it has already seen, or new ones?** If new, the test set must hold only new ones.

### 6.2 A simulation where we know the answer

We create 80 patients with 15 visits each. Every patient has a personal **fingerprint** (a few stable measurements such as height or a lab baseline) and a personal **risk level** that mostly decides whether visits end in a bad outcome. The only generalisable signal is a weak, real one: a shared `symptom_score`.

```python run
def make_patients(n_patients=80, visits=15, seed=0):
    r = np.random.default_rng(seed)
    pid = np.repeat(np.arange(n_patients), visits)
    finger = r.normal(0, 1, (n_patients, 4))                 # stable personal traits
    risk = r.normal(0, 1.6, n_patients)                      # personal tendency (hidden)
    symptom = r.normal(0, 1, n_patients * visits)
    logit = risk[pid] + 0.6 * symptom
    y = (r.random(n_patients * visits) < 1 / (1 + np.exp(-logit))).astype(int)
    X = np.column_stack([finger[pid] + r.normal(0, 0.05, (n_patients * visits, 4)), symptom])
    cols = ["trait_a", "trait_b", "trait_c", "trait_d", "symptom_score"]
    return pd.DataFrame(X, columns=cols), y, pid

Xp, yp, pid = make_patients()
print(Xp.shape, "| patients:", len(set(pid)), "| bad-outcome rate:", round(yp.mean(), 3))
print(Xp.head(4).round(3).to_string())
```

Random folds put some of a patient's visits in training and the rest in test. A forest recognises the fingerprint. Group folds keep every patient entirely on one side.

### 6.4 Choosing the group

The group is *whatever the model must generalise across*. Examples:

| Prediction task | Group by |
|---|---|
| Diagnose a new patient | patient |
| Read handwriting from a new writer | writer |
| Detect fraud on a card the bank has not seen | card (or customer) |
| Forecast a new store | store |
| Classify new documents | document, or the source of the document |
| Image of an object from a new camera | camera / session |

If you are not sure, choose the **coarser** grouping. A split that is a bit too strict costs you a pessimistic number; a split that is too loose costs you a lie.

## 7. Time-based splits

### 7.1 The future is not a random sample of the past

When data are ordered in time, a random split lets the model train on Tuesday and Thursday and be tested on Wednesday. In real life you never get to know Thursday before predicting Wednesday. Worse, neighbouring days are alike (prices move slowly, seasons repeat), so a model can answer "what happened on Wednesday?" by *interpolating* between two days it has already seen. That is not forecasting.

Two things go wrong at once:

1. **Leakage by interpolation.** Test rows sit between training rows in time.
2. **Hidden change.** The world drifts: trends rise, behaviour changes, new products appear. A random split hides drift because train and test come from the same period.

### 7.2 A demand series where we know the truth

Daily sales for a shop: an upward trend, a weekly pattern, a promotion effect, and some day-to-day noise that lasts a few days.

```python run
def make_sales(n=730, seed=0):
    r = np.random.default_rng(seed)
    t = np.arange(n)
    dow = t % 7
    promo = (r.random(n) < 0.10).astype(int)
    noise = np.zeros(n)
    for i in range(1, n):                                  # noise that persists for a few days
        noise[i] = 0.6 * noise[i - 1] + r.normal(0, 6)
    y = 100 + 0.25 * t + 15 * np.sin(2 * np.pi * dow / 7) + 30 * promo + noise
    return pd.DataFrame({"day": t, "dow": dow, "promo": promo, "sales": y})

sales = make_sales()
print(sales.head(8).round(1).to_string(index=False))
print("first 100 days mean:", round(sales["sales"][:100].mean(), 1), "| last 100 days mean:", round(sales["sales"][-100:].mean(), 1))
```

The random split reports an error several times smaller. It is the wrong number: tomorrow is *after* every training day, and a tree cannot extend an upward trend beyond the largest day number it has seen.

### 7.3 How `TimeSeriesSplit` works

It makes folds where the training window always ends **before** the test window starts. The training set grows with each fold (*expanding window*).

```python run
tss = model_selection.TimeSeriesSplit(n_splits=4)
for k, (tr, te) in enumerate(tss.split(sales)):
    print(f"fold {k}: train days {tr[0]:3d}..{tr[-1]:3d} ({len(tr):3d})   test days {te[0]:3d}..{te[-1]:3d} ({len(te)})")
```
```text
fold 0: train days   0..145 (146)   test days 146..291 (146)
fold 1: train days   0..291 (292)   test days 292..437 (146)
fold 2: train days   0..437 (438)   test days 438..583 (146)
fold 3: train days   0..583 (584)   test days 584..729 (146)
```

Useful options:

| Option | Meaning | Use when |
|---|---|---|
| `max_train_size=N` | **rolling window**: keep only the latest N rows | old data is no longer relevant |
| `test_size=N` | fixed length of every test window | you forecast a fixed horizon (e.g. 7 days) |
| `gap=N` | skip N rows between train and test | the label takes N days to be known, or features look back N days |

The `gap` matters more than people think. If you predict whether a customer will pay within 30 days, the label for a row from 20 days before the cut-off is not known yet at the cut-off. Leave a gap so that training labels were really known at the training cut-off.

### 7.4 Look-ahead features: leakage inside the feature code

Even with a perfect time split, one careless line leaks the future. Rolling averages are the classic: a *centred* window uses days after today.

```python run
s = sales.copy()
s["roll7_past"] = s["sales"].shift(1).rolling(7).mean()                      # uses days t-7..t-1 : fine
s["roll3_centre"] = s["sales"].rolling(3, center=True).mean()                 # uses t-1, t, t+1 : includes today and tomorrow!
s["lag1"] = s["sales"].shift(1)
s["lag7"] = s["sales"].shift(7)
s = s.dropna().reset_index(drop=True)

def time_cv_mae(cols):
    return -model_selection.cross_val_score(hgb, s[cols], s["sales"], cv=model_selection.TimeSeriesSplit(5), scoring="neg_mean_absolute_error").mean()

print("past-only features  (dow, promo, lag1, lag7, roll7_past):", round(time_cv_mae(["dow", "promo", "lag1", "lag7", "roll7_past"]), 2))
print("with centred window (adds roll3_centre)                 :", round(time_cv_mae(["dow", "promo", "lag1", "lag7", "roll7_past", "roll3_centre"]), 2), " <- too good")
```
```text
past-only features  (dow, promo, lag1, lag7, roll7_past): 16.98
with centred window (adds roll3_centre)                 : 13.64  <- too good
```

Notice the second score is better *even with a correct time split*. The split cannot save you from a feature that already contains the answer. The test: for every time-based feature, check that it uses only rows with timestamps **strictly before** the prediction time.

A cheap automatic check: **truncate the future** and recompute the feature. If today's value changes when you delete everything after today, the feature looks ahead.

```python run
def uses_future(feature_fn, series, t=400):
    """Compute the feature on the full series and on the series cut at day t; compare day t."""
    full = feature_fn(series).iloc[t]
    cut = feature_fn(series.iloc[: t + 1]).iloc[t]
    return not np.isclose(full, cut, equal_nan=True)

print("shift(1).rolling(7).mean()   uses the future?", uses_future(lambda x: x.shift(1).rolling(7).mean(), sales["sales"]))
print("rolling(3, center=True).mean uses the future?", uses_future(lambda x: x.rolling(3, center=True).mean(), sales["sales"]))
print("ewm(span=5).mean()           uses the future?", uses_future(lambda x: x.ewm(span=5).mean(), sales["sales"]))
```
```text
shift(1).rolling(7).mean()   uses the future? False
rolling(3, center=True).mean uses the future? True
ewm(span=5).mean()           uses the future? False
```

### 7.5 Proving you can forecast: the seasonal-naive baseline

On time series, the baseline is not "the mean". Good simple baselines are **persistence** ("tomorrow equals today") and **seasonal naive** ("this Tuesday equals last Tuesday"). A model must beat them on a time-ordered test set, or it is not forecasting anything.

```python run
cut = int(len(s) * 0.8)
train_s, test_s = s.iloc[:cut], s.iloc[cut:]
feats = ["dow", "promo", "lag1", "lag7", "roll7_past"]
model_t = ensemble.HistGradientBoostingRegressor(random_state=0).fit(train_s[feats], train_s["sales"])
pred_model = model_t.predict(test_s[feats])
mae = lambda y, p: float(np.mean(np.abs(np.asarray(y) - np.asarray(p))))
print("test period: days", int(test_s["day"].iloc[0]), "to", int(test_s["day"].iloc[-1]))
print(f"persistence     (yesterday)       MAE: {mae(test_s['sales'], test_s['lag1']):.2f}")
print(f"seasonal naive  (same weekday)    MAE: {mae(test_s['sales'], test_s['lag7']):.2f}")
print(f"gradient boosting (past features) MAE: {mae(test_s['sales'], pred_model):.2f}")
```
```text
test period: days 584 to 728
persistence     (yesterday)       MAE: 12.81
seasonal naive  (same weekday)    MAE: 14.06
gradient boosting (past features) MAE: 16.97
```

The flexible model **loses to both naive baselines**. That is a real and common result, and a good reason to run the baseline first. Why did it lose? Sales keep rising, so test-period sales are higher than anything in the training period, and a tree cannot predict a value larger than the ones it has seen:

```python run

print("average sales in the test period      :", round(float(test_s["sales"].mean()), 1))

```

```text
largest sales value seen in training  : 293.5
average sales in the test period      : 269.0
share of test days above the training maximum: 0.11
```

Two repairs, both ordinary craft. Predict the **change** from last week instead of the level (the change does not trend), or use a model that can extrapolate a trend.

```python run
# 1. predict the change from the same weekday last week, then add it back
change_model = ensemble.HistGradientBoostingRegressor(random_state=0).fit(train_s[feats], train_s["sales"] - train_s["lag7"])
pred_change = test_s["lag7"].to_numpy() + change_model.predict(test_s[feats])
# 2. a linear model on the same features (a trend through lag features is natural for it)
ridge_t = linear_model.Ridge(alpha=1.0).fit(pd.get_dummies(train_s[feats], columns=["dow"], dtype=float), train_s["sales"])
pred_ridge = ridge_t.predict(pd.get_dummies(test_s[feats], columns=["dow"], dtype=float))
print(f"seasonal naive                        MAE: {mae(test_s['sales'], test_s['lag7']):.2f}")
print(f"boosting on the level                 MAE: {mae(test_s['sales'], pred_model):.2f}")
print(f"boosting on the change from last week MAE: {mae(test_s['sales'], pred_change):.2f}")
print(f"ridge regression on the level         MAE: {mae(test_s['sales'], pred_ridge):.2f}")
```
```text
seasonal naive                        MAE: 14.06
boosting on the level                 MAE: 16.97
boosting on the change from last week MAE: 11.43
ridge regression on the level         MAE: 6.78
```

Three lessons in one table. (1) The flexible model was not "better" until it was repaired. (2) A boring **linear model won by a wide margin** because the true trend in this series is a straight line, which a linear model can extend and a tree cannot. Model flexibility is not the same as model fitness. (3) None of this was visible with a random split, which gave the boosted tree an error of 5.79 in section 7.2. Only the time-ordered test told the truth.

### 7.6 Drift: why the date of the test set matters

A model trained on the past and tested on the future usually scores *worse* than random cross-validation says. That gap is information: it measures how fast your world changes. Report both, and plan retraining accordingly.

### 7.7 Rules for time splits

1. The test set is **later** than the training set. Always.
2. The validation set sits between them in time. Choose hyperparameters there, then train again on train + validation, then test once.
3. Add a **gap** equal to label delay.
4. Features may only use data timestamped **before** the prediction time.
5. If a customer, device or store appears in many rows, a time split still lets the same entity appear on both sides. That is allowed when the model will see the same entities in production (next month's customers include this month's) and forbidden when it will not. Decide deliberately.
6. Report the period covered by every split. "Trained on 2023, tested on 2024-Q1" is a result; "80/20 split" is not.

## 8. Baselines, business rules and proving you beat them

### 8.1 Why the baseline decides whether the project lives

"AUC 0.76" means nothing alone. Is that good? It is good if the best simple alternative gets 0.60, and uninteresting if a one-line rule gets 0.74. A model must **earn its complexity**: it needs to be monitored, retrained, explained and kept running. The baseline is the price of not building it.

Three kinds of baseline, from cheapest to hardest to beat:

| Baseline | Example | What beating it proves |
|---|---|---|
| **Naive** | predict the majority class or the training mean; "same as last week" | the model learned *something* |
| **Business rule** | "customers on a month-to-month contract with 3 or more support calls are at risk" | the model beats what the business already does or would do tomorrow |
| **Simple model** | logistic regression on 3 features | the extra complexity is worth it |

### 8.3 Three baselines and a model

A business rule returns a score too, so we can compare ranking quality with the same metrics. The rule here gives 2 points for a month-to-month contract and 1 point for three or more support calls: a plausible hand-made risk score.

```python run
def rule_score(X):
    return 2 * X["contract_month"].to_numpy() + 1 * (X["support_calls"].to_numpy() >= 3)

def top_decile_lift(y, score):
    """Churn rate among the 10% highest-scored customers divided by the overall churn rate."""
    order = np.argsort(-score, kind="stable")
    k = max(1, len(y) // 10)
    return float(np.mean(y[order][:k]) / np.mean(y))

candidates = {

for name, mdl in candidates.items():
```

### 8.4 "Better" is a difference with an error bar

Two scores differ by 0.02. Is that real or luck? Models are compared on the **same rows**, so the right tool is a *paired* comparison: compute the difference on each fold (or each resample) and look at its spread.

**Step 1: repeated cross-validation on the development set.** The same folds are used for both models, so each fold gives a paired difference.

```python run
rskf = model_selection.RepeatedStratifiedKFold(n_splits=5, n_repeats=4, random_state=0)
m_logit = pipeline.make_pipeline(preprocessing.StandardScaler(), linear_model.LogisticRegression(max_iter=2000))
diffs = []
for tr, te in rskf.split(X_dev, y_dev):
    Xa, Xb_, ya, yb_ = X_dev.iloc[tr], X_dev.iloc[te], y_dev[tr], y_dev[te]
    auc_model = metrics.roc_auc_score(yb_, m_logit.fit(Xa, ya).predict_proba(Xb_)[:, 1])
    auc_rule = metrics.roc_auc_score(yb_, rule_score(Xb_))
    diffs.append(auc_model - auc_rule)
diffs = np.array(diffs)
print(f"{len(diffs)} paired folds: mean AUC gain of model over rule = {diffs.mean():.4f}, std {diffs.std(ddof=1):.4f}")
print(f"model better in {int((diffs > 0).sum())} of {len(diffs)} folds")
```
```text
20 paired folds: mean AUC gain of model over rule = 0.0668, std 0.0144
model better in 20 of 20 folds
```

Folds from the same data are **not independent** (they share rows), so a plain standard error understates the uncertainty. Treat this as a rough guide, not a formal test.

**Step 2: a bootstrap on the sealed test set.** Resample the test rows with replacement many times, and each time compute the AUC of both models on the *same* resample. The spread of the difference is an honest error bar.

```python run
final_model = m_logit.fit(X_dev, y_dev)                    # train on train+validation, as agreed
p_test = final_model.predict_proba(X_test)[:, 1]
s_rule = rule_score(X_test)
rng = np.random.default_rng(0)
gains = []
for _ in range(1000):
    idx = rng.integers(0, len(y_test), len(y_test))
    if y_test[idx].min() == y_test[idx].max():
        continue
    gains.append(metrics.roc_auc_score(y_test[idx], p_test[idx]) - metrics.roc_auc_score(y_test[idx], s_rule[idx]))
gains = np.array(gains)
lo, hi = np.percentile(gains, [2.5, 97.5])
print(f"test AUC  model: {metrics.roc_auc_score(y_test, p_test):.3f}   rule: {metrics.roc_auc_score(y_test, s_rule):.3f}")
print(f"gain (model - rule): {gains.mean():.3f}   95% interval [{lo:.3f}, {hi:.3f}]")
print("interval excludes zero:", bool(lo > 0))
```
```text
test AUC  model: 0.765   rule: 0.691
gain (model - rule): 0.074   95% interval [0.049, 0.099]
interval excludes zero: True
```

If the interval excludes zero, you can say "the model is better than the rule" and give the size. If it includes zero, say "no evidence of a difference" and keep the rule: it is cheaper.

### 8.5 The proof is in the split

Outcome 2 of this chapter is to **beat a baseline and prove it with the right split**. The right split is the one that mimics deployment:

| Situation | Right split | Right baseline |
|---|---|---|
| Next-month customers | train on earlier months, test on the later month | last month's rule or churn rate |
| New patients | `GroupKFold` by patient | clinician's checklist |
| Forecasting | `TimeSeriesSplit` with gap | seasonal naive |
| New stores | group by store | the chain-wide average |

A model that beats a baseline on a random split and loses on the right split has not beaten the baseline. Always test the claim on the split that matches the use.


### 9.1 When one class is rare

Fraud, equipment failure, rare disease, spam to a good inbox: the interesting event is rare. We simulate card transactions where fewer than 1 in 100 is fraud.

```python run
def make_fraud(n=40000, seed=0):
    r = np.random.default_rng(seed)
    amount = np.exp(r.normal(3.6, 1.1, n))                        # skewed, in currency units
    hour = r.integers(0, 24, n)
    tx_24h = r.poisson(2.0, n)
    new_device = (r.random(n) < 0.10).astype(int)
    country_mismatch = (r.random(n) < 0.06).astype(int)
    logit = (-11.4 + 1.1 * np.log(amount) + 2.0 * new_device + 2.4 * country_mismatch
             + 0.3 * tx_24h + 1.2 * ((hour < 5) | (hour > 22)))
    fraud = (r.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return pd.DataFrame(dict(amount=amount, hour=hour, tx_24h=tx_24h, new_device=new_device, country_mismatch=country_mismatch, fraud=fraud))
```

### 9.3 Precision and recall

- **Recall** (sensitivity): of the real frauds, what share did we catch? `TP / (TP + FN)`.
- **Precision**: of the alarms we raised, what share were real frauds? `TP / (TP + FP)`.

Lowering the threshold catches more fraud (recall up) and raises more false alarms (precision down). The **precision-recall curve** shows the whole trade.

### 9.4 ROC-AUC versus average precision

ROC-AUC measures how well positives are ranked above negatives and is **insensitive to class balance**. With more than 99% negatives, a model can have a high ROC-AUC while its alerts are mostly false, because the false positive *rate* is small when the denominator (negatives) is huge. **Average precision** (the area under the precision-recall curve) is much more sensitive to the rare class. Its baseline is the positive rate, not 0.5.

### 9.5 Handling imbalance: what helps and what does not

| Technique | What it does | Honest use |
|---|---|---|
| **Stratified splits** | keeps the rare class in every fold | always |
| **`class_weight="balanced"`** | makes a rare-class error cost more in training | try it; it changes probabilities (they become inflated) |
| **Under-sampling** the majority | throws away common rows | fast; keep in the training fold only |
| **Over-sampling** (copy or SMOTE) the minority | adds minority rows | **only inside the training fold**, never before splitting |
| **Threshold change** | moves along the precision-recall curve | often the best first step (section 10) |
| **Better features / more data** | actually improves the ranking | the real fix |

Weights change the model but not the problem. Often changing the *threshold* gives the same trade-off as weighting, with no retraining.


### 9.6 The oversampling leak

Over-sampling before splitting is a leak of family 3: the copies of a minority row land on both sides.

```python run
def oversample(X, y, factor, seed=0):
    """Copy every minority row `factor` times (simple random over-sampling)."""
    X = np.asarray(X); y = np.asarray(y)
    pos = np.where(y == 1)[0]
    extra = np.tile(pos, factor - 1)
    return np.vstack([X, X[extra]]), np.concatenate([y, y[extra]])

forest_f = ensemble.RandomForestClassifier(n_estimators=60, min_samples_leaf=1, random_state=0, n_jobs=1)
Xv, yv = Xf.to_numpy(), yf
skf = model_selection.StratifiedKFold(5, shuffle=True, random_state=0)

# LEAKY: oversample the whole dataset, then cross-validate
Xo, yo = oversample(Xv, yv, 10)
leaky_ap = model_selection.cross_val_score(forest_f, Xo, yo, cv=skf, scoring="average_precision").mean()

# HONEST: oversample only inside each training fold; score on untouched folds
ap_scores = []
for tr, te in skf.split(Xv, yv):
    Xtr_o, ytr_o = oversample(Xv[tr], yv[tr], 10)
    ap_scores.append(metrics.average_precision_score(yv[te], forest_f.fit(Xtr_o, ytr_o).predict_proba(Xv[te])[:, 1]))
print(f"leaky  average precision: {leaky_ap:.3f}")
print(f"honest average precision: {np.mean(ap_scores):.3f}")
```
```text

honest average precision: 0.065
```

## 10. Choosing a threshold from a business cost

### 10.1 A model ranks; a decision needs a line

A classifier gives each customer a probability. The business must act: *call* or *do not call*. The threshold is the line between the two, and 0.5 has no special authority. It is the right line only when the two kinds of mistake cost the same and the classes are balanced. In practice almost never.

**The threshold is a business parameter, not a model parameter.** The right way to set it is from costs.

### 10.2 The cost matrix

For the churn problem, suppose the retention team agrees on these rupee costs per customer:

| | Customer stays (0) | Customer churns (1) |
|---|---|---|
| **We do not call** (predict 0) | TN: cost 0 | **FN: cost 100** (a lost customer) |
| **We call** (predict 1) | **FP: cost 20** (a wasted call) | TP: cost 20 (the call is made, and the customer is kept) |

```python run
COST = {"tn": 0, "fp": 20, "fn": 100, "tp": 20}

def total_cost(y_true, y_pred, cost=COST):
    tn, fp, fn, tp = metrics.confusion_matrix(y_true, y_pred, labels=[0, 1]).ravel()
    return tn * cost["tn"] + fp * cost["fp"] + fn * cost["fn"] + tp * cost["tp"]

# Same split as section 8: train / validation / sealed test

p_te = logit_model.predict_proba(X_test)[:, 1]

print(f"call everybody: cost per customer {total_cost(y_val, np.ones(n_val, int)) / n_val:7.2f}")
print(f"threshold 0.5 : cost per customer {total_cost(y_val, p_val >= 0.5) / n_val:7.2f}")
```

### 10.4 The theory behind it

For a model whose probabilities are **correct** (calibrated, section 11), there is a closed form. For a customer with churn probability `p`:

- cost if we call: `p * C_tp + (1 - p) * C_fp`
- cost if we do not call: `p * C_fn + (1 - p) * C_tn`

Call when the first is smaller. Solving for `p`:

```text
call if   p  >  (C_fp - C_tn) / [ (C_fp - C_tn) + (C_fn - C_tp) ]
```

```python run

print(f"theoretical threshold = (20 - 0) / ((20 - 0) + (100 - 20)) = {t_star:.4f}")

```
```text

validation cost per customer at that threshold: 14.78
```

The formula shows the logic: the dearer a miss is relative to a false alarm, the lower the threshold. Equal costs give 0.5. The formula is only as good as the probabilities (a miscalibrated model gives a wrong `p`), which is why section 11 follows.

## 11. Probability calibration

### 11.1 What "calibrated" means

A model is **calibrated** when its probabilities mean what they say: among all customers given a 30% churn probability, about 30% actually churn. Ranking metrics like AUC do not test this at all, because they only look at order. Yet probabilities drive decisions: the threshold formula of section 10.4, expected revenue, risk scores shown to humans.

### 11.2 The reliability table

Group predictions into bins and compare the average predicted probability to the observed frequency in each bin.

```python run
def reliability(y, p, bins=8):
    q = pd.qcut(p, bins, duplicates="drop")
    t = pd.DataFrame({"y": y, "p": p, "bin": q}).groupby("bin", observed=True).agg(n=("y", "size"), predicted=("p", "mean"), observed=("y", "mean"))
    return t.reset_index(drop=True)

def ece(y, p, bins=10):
    """Expected calibration error: average |observed - predicted| over equal-count bins, weighted by size."""
    t = reliability(y, p, bins)
    return float(((t["observed"] - t["predicted"]).abs() * t["n"]).sum() / t["n"].sum())

def calib_report(name, y, p):
    return {"model": name, "AUC": metrics.roc_auc_score(y, p), "Brier": metrics.brier_score_loss(y, p), "log loss": metrics.log_loss(y, p), "ECE": ece(y, p)}

print("logistic regression on the test set:")
print(reliability(y_test, p_te).round(3).to_string())
```

### 11.3 Scores for calibration

| Score | Meaning | Perfect value |
|---|---|---|
| **Brier score** | mean squared error of the probability against 0/1 | 0 (lower is better) |
| **Log loss** | punishes confident wrong answers heavily | 0 |
| **ECE** | average gap between predicted and observed in bins | 0 |

Brier and log loss are *proper scoring rules*: they reward honest probabilities and reflect both ranking and calibration. ECE isolates calibration but depends on the binning.

### 11.5 Fixing it: calibrate on data the model did not train on

Calibration learns a small mapping from the model's raw score to a true probability. The two classic maps:

- **Sigmoid (Platt scaling)**: fits a logistic curve; few parameters, good for small data.
- **Isotonic regression**: fits a free-form increasing step function; flexible, needs more data (about 1,000+ rows) or it overfits.

The mapping must be fitted on rows the base model was **not trained on**, otherwise the model's over-confidence on its own training rows is baked into the map. `CalibratedClassifierCV(cv=5)` does this by cross-fitting: it trains the base model on four folds, calibrates on the fifth, and repeats.

```python run
rows = [calib_report("random forest (raw)", y_test, rf.predict_proba(X_test)[:, 1])]
for method in ["sigmoid", "isotonic"]:
    cal = calibration.CalibratedClassifierCV(ensemble.RandomForestClassifier(n_estimators=150, min_samples_leaf=3, random_state=0, n_jobs=1), method=method, cv=5).fit(X_tr, y_tr)
    rows.append(calib_report(f"random forest + {method}", y_test, cal.predict_proba(X_test)[:, 1]))
print(pd.DataFrame(rows).set_index("model").round(4).to_string())
```

### 11.7 Calibration pitfalls

1. **Calibrating on the training rows** (or with the same rows used to pick hyperparameters) gives a flattering map.
2. **Small data + isotonic** overfits: the step function memorises. Prefer sigmoid below roughly 1,000 calibration rows.
3. **Calibration drifts.** The base rate changes (fraud doubles in December), so a calibrated model can become miscalibrated without any change in ranking. Monitor the reliability table in production.
4. **Calibrated for whom?** A model can be calibrated overall and badly off for a subgroup (section 12). Check reliability per segment.
5. **Reweighting breaks it**: `class_weight` and resampling inflate probabilities (section 9.5). Calibrate afterwards on data with the true class mix.

## 12. Error analysis by subgroup and segment

### 12.1 One number hides the structure

A model with AUC 0.76 may be superb for half the customers and useless for the other half. The overall score is an average, and averages hide the cases that matter: the segment the business cares about most, the segment where mistakes are harmful, the segment that is growing. **Error analysis** is the habit of asking *where* the model is wrong, not only *how often*.

### 12.3 The slice table

For each value of a grouping column, compute: how many rows, the true rate, the average predicted rate, the AUC and a bootstrap interval for the AUC (small slices have wide intervals; ignore a difference smaller than its noise).

```python run
def auc_ci(y, p, reps=300, seed=0):
    if len(set(y)) < 2:
        return (np.nan, np.nan, np.nan)
    r = np.random.default_rng(seed)
    vals = []
    for _ in range(reps):
        i = r.integers(0, len(y), len(y))
        if len(set(y[i])) == 2:
            vals.append(metrics.roc_auc_score(y[i], p[i]))
    return (metrics.roc_auc_score(y, p), *np.percentile(vals, [2.5, 97.5]))

def slice_table(frame, y, p, col):
    rows = []
    for value, idx in frame.groupby(col, observed=True).indices.items():
        a, lo, hi = auc_ci(y[idx], p[idx])
        rows.append((value, len(idx), y[idx].mean(), p[idx].mean(), a, lo, hi))
    return pd.DataFrame(rows, columns=[col, "rows", "true rate", "predicted rate", "AUC", "AUC lo", "AUC hi"]).set_index(col)
```

### 12.5 Automatic slice scan

Looking at a few columns by hand misses things. Scan all single columns and pairs, require a minimum size, and rank slices by how much worse than the overall model they are (here: log loss, which reacts to both ranking and probability errors).

```python run
def worst_slices(frame, y, p, cols, min_rows=120, top=6):
    overall = metrics.log_loss(y, p)
    found = []
    import itertools
    for k in (1, 2):
        for combo in itertools.combinations(cols, k):
            for key, idx in frame.groupby(list(combo), observed=True).indices.items():
                if len(idx) < min_rows or len(set(y[idx])) < 2:
                    continue
                found.append((" & ".join(f"{c}={v}" for c, v in zip(combo, np.atleast_1d(key))), len(idx), metrics.log_loss(y[idx], p[idx], labels=[0, 1]) - overall))
    out = pd.DataFrame(found, columns=["slice", "rows", "log-loss gap vs overall"])
    return out.sort_values("log-loss gap vs overall", ascending=False).head(top).reset_index(drop=True)
```

### 12.7 What to do with a weak segment

| Finding | Action |
|---|---|
| A feature is missing for that segment | collect it |
| The segment is tiny | gather more data, or state "unreliable" and use a rule there |
| The segment behaves differently | a separate model, or an interaction feature |
| Labels are noisy there | fix the labelling |
| The segment is a protected group | stop and review fairness (equal error rates, calibration within groups) before deployment |
| Nothing helps | document the limit; route to a human or to the baseline |

### 12.8 Subgroup honesty

Rules for slicing:

1. **Choose slices before looking at results** when you can (by business meaning). Scanning hundreds of slices will always find some that look bad by luck. This is the multiple-comparison problem; treat a scan as a source of hypotheses, then confirm the interesting slice on fresh data.
2. **Always show the row count** and an interval.
3. **Compare calibration per slice**, not just ranking.

## 13. Reproducibility

### 13.1 Why reproducibility is part of evaluation

A result nobody can reproduce is an anecdote. Reproducibility matters for three practical reasons:

1. **You will need to rerun it.** In three months someone asks "which model did we ship and what was its score?". Without a record you cannot answer.
2. **You cannot debug what you cannot repeat.** If a model's score moves by 0.02 each time you run it, you cannot tell whether your change helped.
3. **Trust.** A reviewer who gets different numbers will stop believing the rest.

Reproducible means: **same data + same code + same settings + same environment = same result**. Each of those four needs to be pinned down.

### 13.2 Where randomness hides

| Source | Controlled by |
|---|---|
| The train/test split | `random_state` in `train_test_split` and in the CV splitter |
| The model's own randomness (forest, boosting, initial values) | the model's `random_state` |
| Shuffling and sampling | the `random_state` or a `Generator` you create with a seed |
| NumPy's global random state | prefer `np.random.default_rng(seed)`; avoid `np.random.seed` |
| Python's `random` module and string `hash()` | `random.seed`, the `PYTHONHASHSEED` variable |
| Parallel jobs (`n_jobs`) | usually fine, but the *order* of floating-point sums can differ in some libraries |
| Row order from a database query without `ORDER BY` | add `ORDER BY`; sort explicitly |
| Library versions | pin versions (section 13.5) |

## 14. Training-serving consistency

### 14.1 Two worlds, one model

A model lives twice. In **training** (offline) it sees a table in a notebook, prepared by pandas and SQL. In **serving** (online) it sees a single request, prepared by application code written by a different person, often in a different language. Any difference in how the features are built is **training-serving skew**, and it silently degrades predictions. The model is the same; the *inputs* are not.

Typical causes:

| Cause | Example |
|---|---|
| **Separate code paths** | training uses a SQL query, serving re-implements it in Python with a different rounding |
| **Column order or naming** | features passed as a plain list in a different order |
| **Categories** | `get_dummies` on one row creates different columns than on the training table |
| **Units and scales** | training in rupees, serving in paise |
| **Missing value handling** | training fills with the median, serving fills with 0 or crashes |
| **Time windows** | "calls in the last 30 days" computed to different cut-offs |
| **Staleness** | batch feature updated nightly, but evaluated as if live |
| **Library versions** | model pickled with one version and loaded with another |

### 14.2 Failure 1: column order (silent)

If you train on a bare array, the model has no idea what the columns mean. If serving sends the same numbers in a different order, nothing fails.

### 14.4 Failure 3: units and ranges (a validator)

If serving sends `monthly_charge` in paise (100 times larger), a linear model extrapolates wildly, and nothing complains. Guard the front door with an explicit schema that records what training saw.

```python run
def make_schema(df, cols):
    return {c: {"min": float(df[c].min()), "max": float(df[c].max())} for c in cols}

def validate_row(schema, row, slack=0.5):
    problems = []
    for c, rng_ in schema.items():
        if c not in row or row[c] is None:
            problems.append(f"{c}: missing")
            continue
        span = rng_["max"] - rng_["min"]
        if row[c] < rng_["min"] - slack * span or row[c] > rng_["max"] + slack * span:
            problems.append(f"{c}={row[c]} is far outside training range [{rng_['min']}, {rng_['max']}]")
    return problems

num_cols = ["tenure_months", "monthly_charge", "support_calls"]
schema = make_schema(data.loc[X_tr.index], num_cols)
print(validate_row(schema, {"tenure_months": 3, "monthly_charge": 95.0, "support_calls": 5}))
print(validate_row(schema, {"tenure_months": 3, "monthly_charge": 9500.0, "support_calls": None}))
```

### 14.5 Failure 4: two code paths

The most durable fix is **one feature function used by both**, living in a module that both import. Training calls it on a table, serving calls it on a one-row table. (The module is also what makes saving work: `pickle` stores a function only as a *name* like `features.build_features`, so the file must exist, unchanged, wherever the model is loaded. A function defined inside a notebook cannot be pickled by name, which is one more reason to keep feature code in a module.)

```python run
features_src = '''

    out = pd.DataFrame(index=raw.index)

    out["is_month_to_month"] = (raw["contract"] == "month").astype(int)

    return out
```

### 14.7 Monitoring for drift: the population stability index

Even a perfect pipeline meets a changing world. Compare the distribution of each feature in production with training. The **population stability index (PSI)** sums, over bins, `(share_now - share_then) * ln(share_now / share_then)`. Common reading: below 0.1 stable, 0.1 to 0.25 moderate shift, above 0.25 major shift (a convention, not a law).

```python run
def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected)
    a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-4, None), np.clip(a, 1e-4, None)
    return float(((a - e) * np.log(a / e)).sum())

train_charge = data.loc[X_tr.index, "monthly_charge"].to_numpy()
r = np.random.default_rng(0)
same_month = r.choice(train_charge, 2000)                    # production looks like training
price_rise = r.choice(train_charge, 2000) * 1.15              # prices went up 15%
paise_bug = r.choice(train_charge, 2000) * 100                # unit bug
for name, arr in [("same distribution", same_month), ("15% price rise", price_rise), ("paise instead of rupees", paise_bug)]:
    print(f"{name:25s} PSI = {psi(train_charge, arr):7.3f}")
```
```text
same distribution         PSI =   0.002
15% price rise            PSI =   0.191
paise instead of rupees   PSI =   8.283
```

PSI would have flagged the paise bug on the first day and the price rise within weeks. Run it on every important feature and on the **model's output scores**, on a schedule.

### 14.8 A short consistency checklist

1. One function builds features, imported by both training and serving.
2. The saved artefact is the **whole pipeline**, from raw input to probability.
3. Inputs are named, validated against a schema, and missing values have one agreed treatment.
4. An equivalence test (batch = one-at-a-time = reloaded) runs in CI.
5. Library versions are pinned and recorded with the artefact.
6. Feature and score distributions are monitored (PSI) in production.
7. Features that are slow to compute online are given the same freshness in training (do not train on up-to-the-second values you will only have nightly).

```python run
def make_loans(n=7000, n_customers=700, seed=3, n_vendor=200):
    r = np.random.default_rng(seed)
    cust_effect = r.normal(0, 1.4, n_customers)               # hidden: some borrowers are just riskier
    cust_birth = r.integers(1950, 2003, n_customers)
    cust_post = r.integers(0, 400, n_customers)
    cid = r.integers(0, n_customers, n)
    day = np.sort(r.integers(0, 730, n))
    income = np.exp(r.normal(10.6, 0.5, n)).round(-2)
    debt_ratio = np.clip(r.beta(2.5, 5, n), 0.02, 0.95).round(3)
    amount = np.exp(r.normal(11.2, 0.6, n)).round(-3)
    score = np.clip(r.normal(650, 70, n), 300, 850).round()
    emp = np.clip(r.gamma(2, 3, n), 0, 40).round(1)
    logit = (-3.4 + 3.0 * (debt_ratio - 0.3) - 0.012 * (score - 650) + 0.35 * (amount / income - 1.0)
             - 0.04 * emp + 0.0012 * day + cust_effect[cid])      # default risk drifts upward over time

    df["default"] = default
    dup = df.sample(frac=0.06, random_state=1)                    # the faulty import loaded 6% of rows twice
    return pd.concat([df, dup], ignore_index=True).sort_values(["application_day", "loan_id"], kind="stable").reset_index(drop=True)
```

### 15.2 The colleague's pipeline, as a function with switches

To measure the effect of each repair, the pipeline below is written once with **switches**. With every switch off it is the colleague's notebook exactly. Each switch turns on one fix.

| Switch | Off (the notebook) | On (the fix) |
|---|---|---|
| `drop_leak` | uses every column | drops `collections_calls` |
| `dedupe` | keeps duplicated loans | drops repeated `loan_id` |
| `honest_prep` | target-encodes postcode, scales, selects 25 columns on **all** rows, then splits | does all three inside the training fold only |
| `split` | random rows | `"group"` (by customer) or `"time"` (earlier loans train, later loans test) |

```python run
BASE = ["income", "debt_ratio", "loan_amount", "credit_score", "employment_years", "birth_year", "application_day"]

def evaluate(d, *, drop_leak, dedupe, honest_prep, split, shuffle_labels=False, model="forest", gap=0, seed=0):
    d = d.copy()
    if dedupe:
        d = d.drop_duplicates("loan_id")
    y = d["default"].to_numpy()
    if shuffle_labels:
        y = np.random.default_rng(seed).permutation(y)
        d["default"] = y
    vendor = [c for c in d.columns if c.startswith("vendor_")]
    cols = BASE + vendor + ([] if drop_leak else ["collections_calls"])
    n = len(d)
    if split == "random":
        tr, te = model_selection.train_test_split(np.arange(n), test_size=0.25, random_state=seed)
    elif split == "group":
        tr, te = next(model_selection.GroupShuffleSplit(1, test_size=0.25, random_state=seed).split(d, y, d["customer_id"]))
    else:                                                      # time: rows are sorted by application_day
        cut = int(n * 0.75)
        tr, te = np.arange(cut - gap), np.arange(cut, n)
    est = (ensemble.RandomForestClassifier(n_estimators=100, random_state=seed, n_jobs=1) if model == "forest"
           else linear_model.LogisticRegression(max_iter=3000))
    if not honest_prep:
        X = d[cols + ["postcode"]].copy()
        X["postcode"] = d.groupby("postcode")["default"].transform("mean")          # target encoding on ALL rows
        Xs = preprocessing.StandardScaler().fit_transform(X)                         # scaler on ALL rows
        keep = feature_selection.SelectKBest(feature_selection.f_classif, k=25).fit(Xs, y).get_support()   # selection on ALL rows
        est.fit(Xs[tr][:, keep], y[tr])
        p = est.predict_proba(Xs[te][:, keep])[:, 1]
    else:
        pre = compose.ColumnTransformer([("pc", preprocessing.TargetEncoder(random_state=seed), ["postcode"])], remainder="passthrough")
        pipe = pipeline.Pipeline([("pre", pre), ("scale", preprocessing.StandardScaler()), ("sel", feature_selection.SelectKBest(feature_selection.f_classif, k=25)), ("clf", est)])
        X = d[cols + ["postcode"]]
        pipe.fit(X.iloc[tr], y[tr])
        p = pipe.predict_proba(X.iloc[te])[:, 1]
    return {"auc": metrics.roc_auc_score(y[te], p), "accuracy": metrics.accuracy_score(y[te], p > 0.5)}

claim = evaluate(loans, drop_leak=False, dedupe=False, honest_prep=False, split="random")
print(f"reproduced the claim: accuracy {claim['accuracy']:.3f}, AUC {claim['auc']:.3f}")
```

### 15.4 The repair waterfall

We now repair the flaws **in order**, and record the test AUC after each. This shows how much each flaw was worth. The order matters because some flaws hide others: the target-encoded postcode carries borrower identity, so a group split cannot show its effect until the encoding is fixed too.

```python run
steps = [
    ("0. the notebook as received",            dict(drop_leak=False, dedupe=False, honest_prep=False, split="random")),
    ("1. drop collections_calls (target leak)", dict(drop_leak=True,  dedupe=False, honest_prep=False, split="random")),
    ("2. remove duplicate loans",               dict(drop_leak=True,  dedupe=True,  honest_prep=False, split="random")),
    ("3. prep inside the training fold",        dict(drop_leak=True,  dedupe=True,  honest_prep=True,  split="random")),
    ("4. split by customer (group)",            dict(drop_leak=True,  dedupe=True,  honest_prep=True,  split="group")),
    ("5. split by time (deployment-like)",      dict(drop_leak=True,  dedupe=True,  honest_prep=True,  split="time")),
]
rows = []
for name, kw in steps:
    out = evaluate(loans, **kw)
    rows.append((name, out["auc"], out["accuracy"]))
waterfall = pd.DataFrame(rows, columns=["stage", "test AUC", "test accuracy"]).set_index("stage")
waterfall["AUC lost vs previous"] = -waterfall["test AUC"].diff()
print(waterfall.round(3).to_string())
```

Read the waterfall from top to bottom. The first fix removes most of the apparent skill, and the next three each remove more. Step 5 is different in kind: it does not remove a flaw, it changes the question to "how well do we predict *later* loans?", and a single split of this size can move either way by a couple of points (the default rate also rises over time, which makes the later period a little easier to rank). Do not read the small rise as the model improving. By the end the number is a statement about what the model can do **on next quarter's loans**, which is the only thing the business cares about.

### 15.5 The honest evaluation

Now do it properly. The design:

1. Sort by time. The last 25% of rows are the **sealed test set**. A **gap** of 600 rows (about 60 days, the time it takes for a default label to be known) separates it from the data used to build the model.
2. All choices (which model, which threshold) are made on the development part with `TimeSeriesSplit` and the same gap.
3. Compare against two baselines: a **rule** and a **dummy**.
4. Evaluate on the test set **once**.

```python run
U = loans.drop_duplicates("loan_id").reset_index(drop=True)
Uy = U["default"].to_numpy()
GAP = 600
cut = int(len(U) * 0.75)
dev_idx, test_idx = np.arange(cut - GAP), np.arange(cut, len(U))
dev, test = U.iloc[dev_idx], U.iloc[test_idx]
print(f"development: days {int(dev['application_day'].min())}-{int(dev['application_day'].max())} ({len(dev)} loans, default {dev['default'].mean():.3f})")
print(f"gap       : {GAP} loans left out")
print(f"sealed test: days {int(test['application_day'].min())}-{int(test['application_day'].max())} ({len(test)} loans, default {test['default'].mean():.3f})")

FEATS = [c for c in BASE if c != "application_day"] + ["postcode"]              # no raw date; the model must not just learn "later = riskier"
def make_pipe(est):
    pre = compose.ColumnTransformer([("pc", preprocessing.TargetEncoder(random_state=0), ["postcode"])], remainder="passthrough")
    return pipeline.Pipeline([("pre", pre), ("scale", preprocessing.StandardScaler()), ("clf", est)])

def rule_risk(frame):
    """Hand-made underwriting rule: weak credit score, high debt ratio, or a big loan relative to income."""
    return ((frame["credit_score"] < 600).astype(int) + (frame["debt_ratio"] > 0.45).astype(int)
            + (frame["loan_amount"] / frame["income"] > 1.6).astype(int)).to_numpy().astype(float)

models = {
    "logistic regression": make_pipe(linear_model.LogisticRegression(max_iter=3000)),
    "random forest": make_pipe(ensemble.RandomForestClassifier(n_estimators=150, min_samples_leaf=10, random_state=0, n_jobs=1)),
}
tss = model_selection.TimeSeriesSplit(n_splits=3, gap=GAP)
cv_rows = []
for name, mdl in models.items():
    fold_auc = model_selection.cross_val_score(mdl, dev[FEATS], dev["default"], cv=tss, scoring="roc_auc")
    cv_rows.append((name, fold_auc.mean(), fold_auc.std(ddof=1)))
fold_rule = [metrics.roc_auc_score(dev["default"].iloc[te_], rule_risk(dev.iloc[te_])) for _, te_ in tss.split(dev)]
cv_rows.append(("hand-made rule", float(np.mean(fold_rule)), float(np.std(fold_rule, ddof=1))))
cv_rows.append(("dummy (prior)", 0.5, 0.0))
print(pd.DataFrame(cv_rows, columns=["model", "time-CV AUC mean", "std over 3 folds"]).set_index("model").round(3).to_string())
```

### 15.6 Threshold from a business cost

The bank's cost for one loan decision:

| | Borrower repays | Borrower defaults |
|---|---|---|
| **Approve** | gain (cost 0) | **loss 5,000** (FN: we approved a defaulter) |
| **Reject** | **lost margin 500** (FP: we turned away a good borrower) | avoided (cost 0) |

Here "positive" means "predicted to default → reject". The costs: `fp = 500` (a good borrower rejected), `fn = 5000` (a defaulter approved), `tp = 0`, `tn = 0`. The theory threshold is `500 / (500 + 5000) = 0.0909`. We choose from **out-of-fold predictions on the development set**, not from the test set.

```python run
LOAN_COST = {"tn": 0, "fp": 500, "fn": 5000, "tp": 0}
oof = np.full(len(dev), np.nan)
for tr_i, te_i in tss.split(dev):
    oof[te_i] = models[chosen_name].fit(dev.iloc[tr_i][FEATS], dev.iloc[tr_i]["default"]).predict_proba(dev.iloc[te_i][FEATS])[:, 1]
have = ~np.isnan(oof)
grid = np.round(np.arange(0.02, 0.60, 0.02), 2)
oof_cost = [total_cost(dev["default"].to_numpy()[have], oof[have] >= t, LOAN_COST) / have.sum() for t in grid]
t_dev = float(grid[int(np.argmin(oof_cost))])
t_theory = LOAN_COST["fp"] / (LOAN_COST["fp"] + LOAN_COST["fn"])
print(f"best threshold on development out-of-fold predictions: {t_dev:.2f} (theory {t_theory:.3f})")

final = models[chosen_name].fit(dev[FEATS], dev["default"])            # refit on the whole development set
p_test = final.predict_proba(test[FEATS])[:, 1]
n_t = len(y_t)
print()
for name, pred in [("approve everybody", np.zeros(n_t, int)), ("reject everybody", np.ones(n_t, int)),
                   ("accuracy-style threshold 0.5", p_test >= 0.5), (f"chosen threshold {t_dev:.2f}", p_test >= t_dev),
                   ("hand-made rule (reject if 2+ red flags)", rule_risk(test) >= 2)]:
    print(f"{name:42s} cost per loan on TEST: {total_cost(y_t, pred, LOAN_COST) / n_t:8.1f}   rejects {np.mean(pred):.0%} of applicants")
```

## 16. Common traps

| Trap | What happens | Fix |
|---|---|---|
| Scaling, imputing, selecting, encoding before splitting | information from test rows enters the model | put every fitted step in a `Pipeline` (3) |
| Target encoding on all rows | each row's label sits in its own feature | cross-fitted or train-only encoding (3.5) |
| A column recorded after the outcome | a near-perfect, useless model | timeline question for each column; single-feature scan (4) |
| "Too good" scores accepted | months lost in production | investigate every surprise; shuffled-label check (1.4, 4.4) |
| Duplicates across the split | memorisation rewarded | deduplicate first; split by group (5) |
| Random folds with repeated entities | optimistic score | `GroupKFold` / `StratifiedGroupKFold` by the unit you generalise across (6) |
| Random split of time-ordered data | interpolation instead of forecasting | `TimeSeriesSplit` with a gap (7) |
| Look-ahead features (centred windows, "current status") | future leaks in through feature code | truncate-the-future test (7.4) |
| Using a flexible model without checking a naive one | complexity that loses to "same as last week" | seasonal naive, rule, dummy first (7.5, 8) |
| Reporting a gain without an error bar | luck mistaken for progress | paired bootstrap on the sealed test set (8.4) |
| Accuracy on rare classes | 99% for a useless model | precision-recall, average precision (9) |
| Resampling before splitting | copies in both sides | resample inside the training fold only (9.6) |
| `class_weight` then trusting probabilities | probabilities inflated | recalibrate on true-mix data (9.5, 11) |
| Default 0.5 threshold | wrong trade of misses and false alarms | choose from costs on validation data (10) |
| Calibrating on the training rows | flattering reliability | cross-fitted calibration; check per segment (11) |
| Judging calibration by ECE alone | a degenerate model looks fine | read Brier and log loss too (11.4) |
| Only the overall score | a failing segment hidden | slice tables with row counts and intervals (12) |
| Scanning many slices and believing the worst | multiple-comparison luck | treat as hypotheses; confirm on fresh data (12.8) |
| Picking the lucky seed | optimism by selection | one fixed seed plus the spread over many (13.4) |
| No record of a run | cannot repeat or explain it | config, data fingerprint, environment, commit (13) |
| Serving with unnamed or reordered columns | silent wrong answers | named columns, whole pipeline saved (14.2, 14.3) |
| Two implementations of the same feature | training-serving skew | one function; equivalence test in CI (14.5, 14.6) |
| No monitoring after launch | drift unnoticed | PSI on features and scores (14.7) |

## 17. Summary

- A score that looks too good is a **question**, not a prize. Most of the time the evaluation, not the model, is wrong.
- **Data leakage** has four families: **target leakage** (a column made after or from the outcome), **preprocessing leakage** (learned statistics computed on all rows), **split leakage** (duplicates, repeated entities), and **time leakage** (the future). Selection by test score is a fifth.
- The golden rule: **everything that learns must be fitted on training rows only** and applied to the rest. A scikit-learn `Pipeline` enforces this inside cross-validation.
- Hunt leaks with the **timeline question**, **single-feature scores**, **importances**, the **shuffled-label check**, duplicate checks, and by asking the data owner.
- **Split the way the model will be used**: by **group** when it will meet new entities (`GroupKFold`, `StratifiedGroupKFold`), by **time** when it will predict the future (`TimeSeriesSplit` with a gap, features from the past only). Random splits are optimistic whenever the world is grouped or ordered.
- **Beat a baseline and prove it**: naive baseline, business rule and simple model; paired comparisons with an error bar (repeated CV, then a bootstrap on the sealed test set); on the split that matches deployment. A flexible model can lose to "same as last week".
- **Class imbalance**: accuracy lies; use the confusion matrix, **precision, recall** and **average precision**. ROC-AUC ignores base rate; weights and resampling change probabilities; resample only inside the training fold.
- **Choose the threshold from a business cost**: sweep thresholds on validation data, or use `C_fp / (C_fp + C_fn)` for calibrated probabilities; report the test cost once. If capacity is the constraint, use top-k.
- **Calibration** asks whether 30% means 30%. Check the reliability table, Brier score and log loss. Fix with sigmoid or isotonic calibration fitted on data the model did not train on. Do not trust ECE alone.
- **Error analysis**: slice by segment, show row counts and intervals, read the confident mistakes, and treat slice scans as hypotheses.
- **Reproducibility**: seeds everywhere, a data fingerprint, environment versions, a config object, an experiment record, a test that runs twice. Report the spread over seeds.
- **Training-serving consistency**: one feature function, the whole pipeline saved, named and validated inputs, an equivalence test, and drift monitoring with PSI.

You reached the three outcomes: you can **find the leak in a model that looks too good** (sections 3 to 6 and the audit), **beat a simple baseline and prove it with the right split** (sections 7 and 8), and **choose a threshold from a business cost** (section 10). The project turned a 0.98 AUC claim into an honest number you could defend.
